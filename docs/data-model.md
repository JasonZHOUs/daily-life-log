# 数据模型与同步（Phase 0 梳理，2026-10-29）

## 存在哪里

| 位置 | 内容 |
|---|---|
| 浏览器 localStorage | 整个状态 `S`（JSON）。**改动后**按模式分槽：`dl1:local`（仅在本设备）、`dl1:u:<用户id>`（某个账号）。旧版的 `dl1` 在第一次打开某个槽时复制进去，并保留为 `dl1:legacy` 备份。界面语言 `dl1:lang`，上次选择的模式 `dl1:mode`。 |
| Supabase `public.days` | 每天一行：`(user_id, day, data jsonb, updated_at)`，`data` 就是下面的“某一天”对象。 |
| Supabase `public.cfg` | 每个账号一行：foods（自定义食物）、dbx（在线找到的食物）、t（目标与身体数据）、gm（记住的克数）、meals（最近的餐）、tpl（每周计划模板）、lang。 |

## 某一天（`S.days['YYYY-MM-DD']`）

| 字段 | 含义 |
|---|---|
| food[] | 饮食：`{b 英文名, z 中文名, g 克, k 千卡, p 蛋白, f 脂肪, c 碳水, at 记录时间戳(新)}` |
| sp {} | 补剂：`{补剂id: true}`，id 见 `SUPS`；`supp` = 早上+晚上全部吃齐（派生） |
| plan[] | 计划：`{t 时间, n 英文, z 中文, x 已勾选, auto 由记录自动勾选(新)}` |
| gym[] / wk[] | 健身部位 / 训练记录 `{x 动作, s:[{r 次数, kg}]}` |
| min {study,lab,ai,career} | 各类时间（分钟） |
| ex[] | 运动消耗 |
| mood, nrg, sl, h2o, stp | 心情 1–5、精力 1–5、睡眠小时、饮水杯数、步数 |
| eng | 口语练习 |
| win, next | 睡前小结：今天的收获、明天三件事 |
| wt | 体重 |
| _t | 最后修改时间（毫秒），同步时新者胜 |

## 同步逻辑

- 本地优先：每次修改先写 localStorage，0.9 秒后把改过的日期 upsert 到 `days`；配置改动 upsert 到 `cfg`。失败 20 秒后重试，恢复联网时也会重试。
- 登录后 `pull()`：逐日比较 `_t`，服务器更新的覆盖本地，本地更新的标记为待上传；服务器没有的本地日期也上传。
- 切回前台时再 `pull()` 一次（正在输入时不拉，避免打断）。

## 梳理时发现的问题（本次已修）

1. **两种模式共用同一份本地数据**：先用“仅在本设备”记录、再登录，本地记录会被上传并混进账号；退出登录后账号数据仍留在本地，再选“仅在本设备”时会把账号数据当成本地数据继续用。→ 改为按模式分槽，互不覆盖。
2. **“仅在本设备使用”不会被记住**：每次打开都要再点一次。→ 记住上次的选择。
3. **跨午夜串天**：App 放在后台过夜时，“今天”还停在昨天，新记录会记到前一天。→ 每分钟和切回前台时检查日期，如果正在看“今天”就自动翻到新的一天。
4. **日期计算**：全部使用设备本地时区（在新加坡即 Asia/Singapore），没有用 UTC 判断“今天”的地方；`toISOString` 只用于同步的 `updated_at` 时间戳。
5. **语言**：默认改为中文；登录页的 “Email”、周柱状图的 “m” 等硬编码英文改为随语言切换。
